## Entry enumeration and scopes

`GET /orgs/{orgId}/users/{userId}/entries` is described as listing all entries a user has access to. Its schema declares **only** integer `orgId` and `userId` path parameters. It declares no `limit`, `offset`, `filter`, `options`, `remoteOnly`, credential identifier, or mobile flag. Its 200 response contains top-level `data`, `totalCount`, `filteredCount`, and `meta`; no documented query default explains a zero total. Self-user read scope `o{orgId}-user{userId}:r` is explicitly accepted. Do not transpose pagination or options from another operation into this one. The public description does not explain whether schedules, credential presence, shared zones, or other effective-access conditions affect membership at the instant of this read. [User entries schema](https://openpath.readme.io/reference/listuserentries)

The API concepts explicitly distinguish API/portal roles from physical access: ordinary employees have a role sufficient for the limited mobile APIs; roles do not define door access. Groups confer the union of their access permissions, and zones hold user/group permission assignments and can be shared between organizations. Therefore portal denial and a limited self-user token do not by themselves explain absent entry access. Conversely, having self-user read/write scopes does not grant door access. [Official access concepts](https://openpath.readme.io/docs/key-concepts)

`GET /orgs/{orgId}/entries` and its POST list counterpart list organization entries and support pagination/filtering plus `options=withEffectiveLocationRestriction`. Their accepted scopes are organization dashboard/site/admin/report/configuration and other broader scopes: **neither own-user `:r` nor own-user `:w` appears**. `GET /orgs/{orgId}/entries/{entryId}` likewise requires broader scopes. These are suitable for an authorized administrator's investigation, not a documented fallback for the reported ordinary-user token. `GET /orgs/{orgId}/groups/{groupId}/entries` requires organization-user read/write or broader scopes, and also omits own-user scopes. [Organization entries](https://openpath.readme.io/reference/listentries), [POST listing](https://openpath.readme.io/reference/listentriespost), [entry detail](https://openpath.readme.io/reference/describeentry), [group entries](https://openpath.readme.io/reference/listgroupentries)

## Supported read-only diagnostics

All of the following accept `o{orgId}-user{userId}:r`, so they are documented comparisons for the same own-user context:

| Read | Documented meaning / useful limit |
| --- | --- |
| `GET /orgs/{orgId}/users/{userId}/zones` | Zones the user can access; returned items contain `id` and optional `name`. |
| `GET /orgs/{orgId}/users/{userId}/sites` | Sites of the user; items contain `id` and optional `name`. Site association alone is not proof of door access. |
| `GET /orgs/{orgId}/users/{userId}/groups` | Groups of the user; items contain `id` and optional `name`. Membership alone does not prove which entries that group grants. |
| `GET /orgs/{orgId}/users/{userId}?options=withUserSites,withRoles,withRealUserGroups` | Documented profile expansions; schema has `sites`, `roles`, `realUserGroups`, and `groups`. The docs do not establish that every expansion is returned for every token. |
| `GET /orgs/{orgId}/users/{userId}/credentials` | Existing credential inventory, including Cloud Key variant and credential validity dates. |

The zones/sites/groups/credentials list operations declare `limit` 1–1000, `offset` minimum/default 0, `sort`, `order`, `q`, `filter`, and `preFilter`. Default sort is `name` for zones/sites/groups and `id` for credentials; default order is `asc`; no default `limit` is stated. These responses have top-level counts. Page these operations according to their own contracts; the pagination guide says to advance by returned count and continue until an empty page. None supplies an independently documented substitute list of eligible entry IDs. [Zones](https://openpath.readme.io/reference/listuserzones), [sites](https://openpath.readme.io/reference/listusersites), [groups](https://openpath.readme.io/reference/listusergroups), [profile options](https://openpath.readme.io/reference/describeuser), [credentials](https://openpath.readme.io/reference/listcredentials), [pagination](https://openpath.readme.io/docs/results-pagination)

For IFSS's comparison, direct user and group assignments and their schedules both matter. Official admin documentation allows distinct user-access and group-access schedules. ## Cloud Key and unlock readiness

Current official remote-unlock guidance requires the user to have both a Cloud Key credential and Remote Unlock permission, and requires the entry state to permit remote unlock; Strict Security is given as a counterexample. This makes the reported remote-unlock flag necessary evidence but insufficient evidence of readiness. Nothing in the inspected entry-list contract says missing Cloud Keys cause that list to be empty. [Remote unlock requirements](https://docs.avigilon.com/bundle/alta-open-mobile-app/page/mobile-apps/alta-open/what-is-remote-unlock.htm)

The credential schema has outer `UserCredential.id`, optional nullable outer `startDate`/`endDate` in date-time format, and a `cloudKey` variant containing its own required `id`, optional `name`, and optional nullable `maxDurationSeconds`. The Cloud Key variant has no declared active/status/revoked flag. Credential-type `modelName` and `name` are unrestricted strings, not a reliable enum; identify the structural `cloudKey` variant. The cloud-unlock path uses the **outer credential ID**, not the nested Cloud Key model ID. Date checks support a local readiness assessment but cannot prove final provider authorization. [Credential schema](https://openpath.readme.io/reference/listcredentials), [unlock schema](https://openpath.readme.io/reference/cloudkeyentryunlock)

`POST /orgs/{orgId}/users/{userId}/credentials/{credentialId}/cloudKeyEntryUnlock` accepts required numeric `entryId` and optional description, accepts own-user write scope, and declares success as 204 with no response body. The schema describes a cloud-unlock request; it does not promise physical-door confirmation, idempotency, automatic retry, or a read-only readiness endpoint. This investigation did not invoke it. [Cloud Key unlock](https://openpath.readme.io/reference/cloudkeyentryunlock)
