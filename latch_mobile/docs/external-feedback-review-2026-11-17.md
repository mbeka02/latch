## What the Claude proposal establishes and what it does not

The statements that zones/group membership, Remote Unlock, Cloud Key and entry state matter are consistent with the official model and remote-unlock documentation. Its stronger conclusion that the observed empty lists **prove** no effective zone grant is premature: the mismatch between IFSS's account assertion and actual own-user responses remains the issue to reconcile. The Super Admin distinction is sound: API/portal privileges are separate from personal entry grants. [Access model](https://openpath.readme.io/docs/key-concepts), [remote unlock](https://docs.avigilon.com/bundle/alta-open-mobile-app/page/mobile-apps/alta-open/what-is-remote-unlock.htm)

An administrator-confirmed, exact intended entry ID can support a **separate explicit one-shot Cloud Key unlock test** using the documented operation. It is a real actuator request, not another read-only discovery probe. The public schema does not require a preceding list call, so such a test can distinguish listing from actuator authorization; it does not establish beforehand that an empty user list is irrelevant. A 204 means the documented command succeeded, without proving the physical door opened. A 403 requires the structured provider error and context before diagnosing which condition failed; it is not uniquely “add this user's zone.” The proposed untested script and guessed anchors should not be used as contract evidence. [Cloud Key contract](https://openpath.readme.io/reference/cloudkeyentryunlock)

Neither supplied answer establishes a reason to ship a configured-ID fallback yet. First obtain the same-account profile/context, raw own-user entry names and complete admin organization inventory comparison described in `alta-contract-second-pass-2026-11-17.md`, or have the authorized administrator compare the exact user against the confirmed entry's effective users/schedules. The current app's exact normalized name match is an independent, concrete possibility. Preserve authoritative mapping and actual authorization evidence before changing the discovery model. [Entry users](https://openpath.readme.io/reference/listentryusers), [entry users/schedules](https://openpath.readme.io/reference/listentryuserschedules)
