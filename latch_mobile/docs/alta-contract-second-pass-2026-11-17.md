## Ranked falsifiable hypotheses

1. **The selected namespace authenticates a valid but different identity from the one holding the intended access.** This is an unresolved hypothesis, not an inference that the current namespace is wrong. `POST /auth/login` accepts optional `namespaceId` or `namespaceNickname` (not both). `POST /auth/loginAll` accepts required `email`/`password` plus optional `mfa` and `forMobileLogin`; it accepts **no namespace field** (`additionalProperties:false`). Its 201 `data` is an array, with each match containing `identityId`, optional `identity.id` and `identity.namespace.{id,nickname}`, a token and `tokenScopeList`. The smallest useful new authentication probe is one EU `loginAll` call with the same credentials and no namespace, retaining only match IDs, namespaces and org/user associations. For each match with a usable own-user association, read that profile and own entries with **that match's token**. If every match resolves to the already observed identity/association and empty entries, this explanation is falsified for native password matches in this region. A second identity with the intended entry would demonstrate a small context-selection fix worth implementing. It does not follow that `loginAll` covers external SSO identities or every region. [Login](https://openpath.readme.io/reference/login), [loginAll](https://openpath.readme.io/reference/loginall), [native API-login constraint](https://openpath.readme.io/docs/using-the-api)

2. **The two entry-list routes expose different inventories for this token.** The own-user operation is explicitly “List all entries a user has access to”; its declared parameters are only integer `orgId` and `userId`. The organization route `GET /orgs/{orgId}/entries` is a separate inventory operation and excludes own-user scopes from its published scope alternatives. One same-token `GET /orgs/{orgId}/entries?limit=1&offset=0` is nevertheless a small controlled way to directly test the proposed wrong-route explanation instead of treating the schema as an observed 403. A 403 demonstrates that this token cannot use that inventory route. A 200 nonempty result establishes different inventory visibility; it does **not** establish the user's physical access or make this a safe replacement for the own-user list. A 200 empty result weakens this route explanation. If a successful inventory result needs examination for the named door, page it within an explicit bound rather than inventing a name-filter grammar. [Own-user list](https://openpath.readme.io/reference/listuserentries), [organization list](https://openpath.readme.io/reference/listentries)

3. **The same user has a grant the own-user access calculation is not exposing, or its grant differs from intercom/operator rights.** The intercom-related group name alone cannot decide this. The supplied facts say profile, Cloud Key and group are present but all user access/controller/activity lists are empty, while group assignment reads are denied. This is unresolved provider-side evidence, not proof of missing grants. The narrow external check is for an authorized administrator to compare the exact returned user ID against the exact intended entry's `listEntryUsers`/`listEntryUserSchedules` results and its zone/group configuration. An affirmative exact-user result conflicting with own-user entries is much stronger escalation evidence than another empty auxiliary list. [Entry users](https://openpath.readme.io/reference/listentryusers), [entry users and schedules](https://openpath.readme.io/reference/listentryuserschedules), [zone/group access model](https://openpath.readme.io/docs/key-concepts)

The reported login organization advertises the same Video deployment and `isUnified:true`. This weakens a claim that the two products are wholly unrelated deployments. Those fields still do not identify the actor, credential or access entitlement behind a historical unlock, and they do not rule out the multiple-identity hypothesis. No Video authentication retry is needed to test hypotheses 1–2.

## Routes and switches that do not supply the missing fix

- **`GET /orgs/{orgId}/effectiveScopes`:** I checked the entire published scope list, not its shortened index preview. It accepts organization-wide user/administrative scopes and other organization permissions, but does **not** list `o{params.orgId}-user{params.userId}:r`/`:w` or an identity-self scope. The path has no `userId` to interpolate. Concrete `o14042-user48181847:r` therefore is not the same declared grant as `o14042-user:r`. The response would be useful (`scopes`, `allowedOperationIds`, `isParentOrg`) if authorized, but this is not a newly documented self-service permission-inspection endpoint. A 403 adds little beyond the group denials. [Full contract](https://openpath.readme.io/reference/geteffectivepermissionsfororg)
- **`POST /orgs/{orgId}/entries/list`:** accepts the GET inventory's same filters/options in a JSON body and declares the same broader scopes. It introduces no own-user scope or remote-unlock switch. It is a weaker next probe than GET, which needs no body serialization. [POST list](https://openpath.readme.io/reference/listentriespost)
- **Own-user pagination/expansion:** `listUserEntries` declares no query/body options, credential argument or expansion. Adding pagination, remote flags or `forMobileLogin` to that GET has no documented basis. Its response is `data:[{id,name,zone,...}]` with top-level counts, not a nested `data.entries` object. The reported raw `data:[]` therefore cannot be repaired by a different client-side field mapping. [Contract](https://openpath.readme.io/reference/listuserentries)
- **Profile expansion:** `withUserSites`, `withRoles` and `withRealUserGroups` are documented; a missing optional `groups` or `identity.users` property is not an exhaustive association result and must not override a successful dedicated groups read. The diagnostic code already obtains org/user IDs from the login scope rows and validates the returned profile; it does not substitute `identityId` as `userId`. [Profile](https://openpath.readme.io/reference/describeuser), [login response/context](https://openpath.readme.io/docs/using-the-api)
- **`sharedUsers`:** includes cross-organization users in its summary, but its schema requires broader organization scopes. It is not a documented alternate self-user context enumeration operation. Zone sharing is a supported model; neither this fact nor the current empty own-user lists proves a cross-org bug. [Shared users](https://openpath.readme.io/reference/listsharedusers), [sharing model](https://openpath.readme.io/docs/key-concepts)
